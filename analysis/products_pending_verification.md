## 一、必须优先验证的（会影响数值正确性）

### 1. FY-3D CLM `Cloud_Mask` 的通道维位置 —— 两处权威记录冲突

- 格式说明 **L155**：`Cloud_Mask` Byte **[2000, 2048, 6]**（通道在**最后**）
- 项目 `PLAN.md` **L123**：`Cloud_Mask (6,2000,2048)`（通道在**最前**）

当前定义按**文档**取 `band_axis: 2`。若实测是 `(6,2000,2048)`，取出来的
「通道」就是 2000 行中的某一行，整幅图会完全错乱。

**怎么验**：`tests/test_products.py::test_fy3d_clm_channel_axis_is_correct`
会读真实文件 shape，取最小的那一维下标，与 `band_axis` 比对，不一致就报错。

### 2. `Cirrus_Mask` 行列顺序与 `Cloud_Mask` 相反

- 格式说明 **L179**：`Cirrus_Mask` Byte **[2048, 2000]**
- 而 `Cloud_Mask` 是 `[2000, 2048]`

两者叠图时**必须转置**，否则错位。定义目前只把这个事实写进 notes，没有做转置
（因为 `band_axis` 的精确定位也还没定）。

### 3. FY-3 1KM 与 250M 的经纬度抽点步长差异（已修正，需回归锁定）

- **1KM**：文档 L77-78 / L366「每隔 **5** 像元」，`Line_number="0,5,10..."`，
  400×5=2000 = 1KM 行数 ✓
- **250M**：文档 L79-80 / L393「每隔 **20** 像元」，`Line_number="0,20,40..."`，
  400×20=8000 = 250M 行数 ✓

**这两个值一旦写反，经纬度会整体错位 4 倍**，图上表现为地理参考完全偏移。
已由 `test_geo_step_differs_between_1km_and_250m` 锁定。

### 4. FY-3 `EV_1KM_Emissive` 的通道数：文档自相矛盾

- 维数写作 `[4,2000,2048]`、`Slope` 有 **4** 个 → 4 个通道
- 但 `band_name` 写成 `"20,21,22,22,23"`（5 个数字，22 重复）

按维数与 Slope 数量判定为 **4 通道 `[20,21,22,23]`**。需用真实文件打印
`band_name` 属性确认这 4 个通道的实际编号顺序（若真是 20,21,22,23 则定义正确）。

### 5. FY-3 250M 的系数表名究竟是 `Ceff` 还是 `Coeff`

- 250M 文档 **L373** 写作 `VIS_Cal_Ceff`（[19,3]，`band_name="1-19"`）
- 1KM 文档 **L350** 与实测文件都是 `VIS_Cal_Coeff`

定义给了候选列表（先试 Ceff 再试 Coeff）。需确认真实 250M 文件里到底是哪个。

### 6. FY-3 `SolarZenith` 的 Slope 与其他角度不一致

GEO 文档 L257：`SolarZenith` 的 `Slope = **1.0**`，而 `SensorAzimuth` /
`SensorZenith` / `SolarAzimuth` 都是 **0.01**。但 `valid_range` 又都是
`[0, 18000]`（即 0~180.00 度的 ×100 编码）。

若 Slope 真是 1.0，则 SolarZenith 的 DN 量纲与其他三个角度差 100 倍。
需读真实文件属性确认。

### 7. `SensorZenith` 的 valid_range 文档内部矛盾

- 表格 `valid_range` 行写 `[0, 4095]`
- 同一节的 `Description` 写 `[0, 18000]`

定义暂取 `[0,18000]`（否则 180 度会被截断到 40.95 度）。需实测定夺。

## 二、数值单位类（搞反就差 100 倍）

### 8. FY-2 的 VIS 查找表**已经是百分比**

- `CALChannelVIS` 值域 `0~118.3942`（实测锚点：`lut[0]=0`、`lut.max()=118.3942`）
- 而 FY-4 的 `CALChannel01` 是 `0~1.14` 的**小数**

定义里对 FY-2G 显式写了 `lut_percent: false`，否则反射率会被放大 100 倍。
由 `test_fy2g_vis_lut_not_percent_multiplied` 锁定。

### 9. FY-4B 可见光 LUT 必须 ×100

`CALChannel01` 值域 `0~1.14`，实测 `DN=1000 → 26.2868%`、`DN=4095 → 114.31%`。
定义用 `lut_reflectance`（默认 ×100），由 `test_fy4b_4000m_reflectance_is_percent`
做双向断言（既查上限也查「最大值不能接近 0~1 量级」以防止漏乘）。

### 10. FY-4B 的 LUT FillValue = -65535.0

文档 L674 / L982：`CALChannelXX` 的 `FillValue = -65535.0`。
已作为 `lut_fill: -65535.0` 写进全部 18 个通道字段。

### 11. 地球内/外两种填充值

文档 L686（4KM）/ L314 附近（1KM）：**地球内无效 = 65534，地球外 = 65535**。
两者都要掩成 NaN，否则圆盘内的坏像元会被当成有效值参与统计。
已用 `dn.in_earth_invalid: 65534` 表示，`FieldDef.fill_values` 会合并处理。

## 三、定标链类

### 12. TBB 转换系数的索引基准

`TBB_Trans_Coefficient_A / _B` 各 **6** 个，对应发射通道 **20~25**（文档表5 L157-158）。
所以索引必须按 `通道号 - 20`：

- `EV_1KM_Emissive` 的 `bands=[20,21,22,23]` → 序号 0..3 恰等于 `ch-20` ✓
- `EV_250_Aggr.1KM_Emissive` 的 `bands=[24,25]` → 序号 0,1 **≠** `ch-20`（应为 4,5）

先前实现按数组序号取，会让 b24/b25 套用 b20/b21 的系数，亮温系统性偏差。
已修正，并由 `test_tbb_coefficients_indexed_by_channel_number` 用纯逻辑锁定。

### 13. `pipeline.thermal_data` 不能直接用于 250M 的独立数据集

`pipeline.thermal_data` 靠解析数据集的 `band_name` 推断通道号。1KM 的通道栈写
`"20,21,22,23"` 能解析；但 **250M 的独立数据集写的是 `"Band 24"`**，
解析器只认纯数字，会退回 `ch_no = 20 + band` = **20**，于是用 3.8 µm 的波数
去反演 10.7 µm 通道。

因此 `products/decode.py` 以 YAML 的 `bands: [24]`（有文档支撑）为准显式给通道号，
公式仍全部来自 `calib`，没有第二份实现。

### 14. `IR_Cal_Coeff (6,4,200)` 逐扫描线系数未使用

1KM/250M 文档都定义了 `IR_Cal_Coeff [6,4,200]`（逐扫描线二次定标），
但当前走的是 `Slope` + `TBB_Trans_Coefficient` 链路（后者有真实样本回归，
实测 187–312 K）。两条链的差异需以文档为准核对。

### 15. FY-4B 的公式法（CALIBRATION_COEF）未实现

文档 3.1/3.2 给了公式法：`ρ = SCALE·DN + OFFSET`，`CALIBRATION_COEF` 形状
`[15,2]`（4KM）/ `[3,2]`（1KM）。当前只用 LUT。两种方法应给出一致结果，
建议补一个交叉校验测试。

### 16. LUT 查表用 nearest 还是 linear

`calib.lookup_table` 两种都支持，实测差异小于一个 DN 的斜率。
文档 3.1/3.2 只写「查找表法」，未指明插值方式。当前取 `nearest`。

## 四、FY-2 CSV 容器

### 17. 定标表在业务文件里全为 0

DOC 定标块 2 本应给出 64 级 VIS 反照率表与 1024 级 IR 亮温表，
但**实测 4 个 VIS + 4 个 IR 查找表全零**。因此只能输出原始 DN，
`unit="DN"`、不给 `scale_factor`。若后续拿到含有效定标块的样本，需要新增定标方法。

### 18. 容器没有 DN 填充值

权威文档 Table 4.19~4.23 未定义填充值，实测也无哨兵值。
**不要臆造填充值**；无效行由 `line_quality` / `picture_flag` / `scan_count` 标识。

定义里 8 个通道都显式写了 `dn.no_fill_value: true`，这样解码器不会套用
FY-3 的 65535/65534/65533 兜底（否则会把合法 DN 误判为缺测）。
由 `test_csv_container_has_no_fill_value_declared` 锁定。

### 19. 可能是 1300 行而非 2500 行

文档 L34/L92 明示「2500th (**or 1300th**) row」。本定义与实测样本都按 2500 行。
读取器已按文件长度动态推算记录数，但 1300 行变体尚未验证。

### 20. 文档的段号说明有排版错误

文档 L248 把 IR3/IR4 写成重复的 IR1/IR2、VIS2/VIS3/VIS4 写成重复的 VIS1。
实测段标志为 DOC=1…VIS4=9 连续，以实测为准。

### 21. FY-2 卫星族覆盖

文档 L67 只举例 FY-2C/2D/2E，实测样本是 FY-2G。格式说明 V2.0 可能未覆盖
FY-2F/G/H，需确认新卫星的 CSV 布局是否完全一致。

## 五、FY-2G FDI（HDF5）

### 22. 星下点经度取不到

文档 §1.2 `structNOMFileInfo` 明确有 `fNOMCenterLon` / `fNOMSatHeight` /
`dSamplingAngle` / `dSteppingAngle`（角度单位是**弧度**）。
但实测 `FY2G_FDI_ALL_NOM_20261018_1300.hdf` 的全局属性在 h5py 侧读不出元数据
（`attrs` 为空），需确认这些属性是否挂在某个 HDF5 组下、或需低层 API 读取。

### 23. 逐像元时间未实现

`NOMOBSTIME` 是 MJD 时间 + 每行 5 个参考点，配合 `NOMOBSTimeGridSpace`
（每行 1 列，值为像素间隔，`-1` 表示该行不在有效成像区）做线性插值。
当前定义只把这些数据集标为 table，未实现逐像元时间反算。

### 24. IR LUT 是递减表，不要反转

`CALChannelIR1..4` 是「计数值越大越冷」的**单调不增**表，直接按 DN 索引即可。
实测 173.93~304.59 K、中位 275~285 K。

### 25. VIS 的 valid_range 边界

文档 L146 写 VIS 灰度索引 `0~64`，但 LUT 只有 64 项（`0~63`）。
定义按 `(0,63)` 掩膜，与既有测试用法一致；边界值 64 待确认。

### 26. 不同 FY-2 星的 LUT 值域可能不同

`CALChannelIR1..4` 的 LUT 值域文档未给（只说 1024 float）。
实测 FY-2G 为 173.93~304.59 K。其他星（C/D/E/F/H）需逐星核对。
